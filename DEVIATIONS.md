# Deviations from Hintze et al. (OSF WGDQ4)

Reference implementation: `hintze_osf/Generation Scripts For HPCC/OSFcontinue.py` (the temperature sweep; `OSFtest.py` is the same loop without resume, `OSFmulti.py` is the 4x4 generator/captioner swap). Verified 2026-10-17. Nothing in the OSF project pins package versions; the SLURM scripts show CUDA 12.4 on a V100 with a conda env.

## What Hintze's code actually does (facts that correct SPEC §4.1 as first written)
| Parameter | SPEC §4.1 said | OSF code does | A0 will do |
|---|---|---|---|
| Resolution | 512x512 | SDXL default 1024x1024, then `resize((512,512), LANCZOS)` | Same as code (see D1 if infeasible) |
| Inference steps | 50 | `num_inference_steps=25` | 25 |
| Guidance scale | 7.5 | not set, diffusers default 5.0 | 5.0 |
| Scheduler | verify | not set, model default EulerDiscreteScheduler | EulerDiscreteScheduler |
| Captioner | llava:13b | `model="llava"` / `"llava:latest"` (7B); `llava:13b-v1.6` only appears in the 4x4 swap | `llava:latest`, digest logged (D2) |
| Caption truncation | implied 50 words | none: `response["response"].strip()` is used verbatim | none (Brad, 2026-10-17) |
| Image format | JPEG | PNG, `optimize=True` | PNG |
| Temperature | 0.9 | Ollama `options={"temperature": temp}`; SDXL has no temperature | 0.9 |
| Negative prompt | n/a | none; SDXL config `force_zeros_for_empty_prompt` gives zero negative embeds | same |
| SDXL seed | fixed per step | not set (random every step) | fixed and logged (D3) |

Prompt-encoding quirk in the code: it calls `pipe.encode_prompt(prompt)` and passes `prompt_embeds` and `pooled_prompt_embeds`, plus `prompt_embeds_2`/`pooled_prompt_embeds_2` from an empty prompt. `StableDiffusionXLPipeline.__call__` has no such parameters; they land in `**kwargs` and are ignored (checked on diffusers 0.41.0). Net effect is an ordinary SDXL call with the prompt and no negative prompt. `encode_prompt` tokenizes with CLIP's 77-token limit, so every caption longer than ~75 tokens is cut there: 85% of Hintze's T=0.9 captions are (median 107 tokens), and on average the first 69 words reach the generator. This is the only truncation in Hintze's loop.

## Deviations
- **D1 Resolution: none.** 1024x1024 at 25 steps fits on 8 GB with `enable_model_cpu_offload()` plus `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. After the WSL restart of 2026-10-17 the figures are 5.49 GB peak allocated, 5.63 GB reserved, 15 to 18 s per image warm (`logs/sysmem_policy_retest.log`, confirmed in the smoke run); the earlier 7.0 GB / 10 GB-reserved numbers in `logs/sdxl_vram_check.log` came from a session that had already spilled. Without the allocator setting the retest reserved 7.85 GB and did not spill, so the sysmem-fallback policy was never exercised; we keep the allocator setting regardless. VAE tiling and attention slicing changed nothing, so they are off. We generate at Hintze's resolution and resize to 512 as he did.
- **D2 Captioner tag.** `llava:latest` is a moving tag. We pin the digest Ollama resolved on 2026-10-17, `8dd30f6b0cb1` (LLaVA 1.6, 7B, Q4_0, 4.7 GB), and log it per step. Hintze's runs (2025) most likely used the same LLaVA 1.6 7B Q4_0 build, but the OSF project does not record the digest.
- **D3 Determinism.** SDXL seeds are fixed per (trajectory, step) and logged. Hintze's were random. Same distribution, reproducible draws.
- **D4 Two-pass lockstep.** Hintze ran one trajectory per V100 job with SDXL and Ollama both resident. We alternate SDXL and LLaVA on the GPU and run all trajectories in lockstep. No change to the per-step computation.
- **D5 Package versions.** Hintze's are unrecorded. Ours: torch 2.11.0+cu128, diffusers 0.41.0, transformers 5.20.1 (pinned in `requirements.txt` once the runner exists). Blackwell requires CUDA 12.8 builds.
- **D6 Model CPU offload.** `enable_model_cpu_offload()` and the expandable-segments allocator to fit 8 GB. Same weights and math; only placement differs.
- **D7 Atomic per-step records.** We write `step_NNN.png` + `step_NNN.json` per step; Hintze rewrote one CSV per run after every step. Content is a superset of his log.

- **D8 Prompt path.** The runner calls `pipe(prompt=...)` instead of the OSF `encode_prompt` + `prompt_embeds` route. Same CLIP encoders, same 77-token truncation, same zero negative embeds (see the quirk note above); the extra `*_2` kwargs the OSF code passes are ignored by diffusers either way. Each record logs `prompt_tokens_clip` and `prompt_truncated_by_clip`.
- **D9 Ollama context and client.** Ollama 0.40.5 loads `llava:latest` with `n_ctx = 4096` (its default, from `journalctl -u ollama`); a 512x512 image plus the instruction is 620 prompt tokens. Hintze's Ollama version and context size are unrecorded. We send exactly his request (`prompt`, `images`, `options={"temperature": T}`) through the same `ollama` Python client (0.6.3); the only addition is `keep_alive` for the two-pass unload, which does not affect generation.
- **D10 Caption of the last image.** Hintze computed but never logged the caption of image 99 (his CSV row k holds the prompt that made image k). We store both `prompt` and `caption` per step, so our records are a superset; analysis that compares with his CSVs uses the prompt series.

- **D11 Batching, parallel captions, and hardware (A0-core on RunPod).** `generator.batch` sends several prompts per SDXL call with one `torch.Generator` per prompt, so each (trajectory, step) keeps its own seed; `captioner.parallel` sends several caption requests at once to an Ollama started with `OLLAMA_NUM_PARALLEL`. Neither changes the per-step computation Hintze's code performs, but batched matmuls and a different GPU change floating-point numerics, so A0-core images are not bit-identical to what the laptop would produce (nor were Hintze's V100 images to either). Captions are independent requests, so parallelism does not affect them beyond numerics. The pilot ran unbatched on the laptop; the core's batch size, parallelism and GPU are in its manifest. Measured 2026-10-18: on the laptop, batch 2 vs batch 1 with the same seeds changes images by 0.3 to 0.7/255 mean absolute pixel difference (numerics only). Across GPUs the difference is larger (27/255 between the laptop's RTX 5070 and the pod's RTX Pro 6000 at the same seeds) because `torch.randn` on CUDA does not produce the same tensor on different GPU models: the seeded latent tensors share their first elements but differ elsewhere (sha mismatch). So the core's trajectories are different random draws from the same distribution as the laptop's, not the same draws, which is the situation Hintze's unseeded runs were in anyway. Ollama on the pod is 0.40.6 (laptop 0.40.5) and, with 8 slots, allocates a 32,768-token context per slot instead of the laptop's 4,096; the 620-token image prompt plus a caption fits in both, so generation is unaffected.

## Planned variants (not A0)
- **A0-trunc (was "P0a").** Hard-truncate each caption to 50 words before it is used as the next prompt. Tests whether an explicit word limit changes the attractors. Needs its own prediction before it runs.
- **A0-long.** Encode captions beyond 77 tokens by chunking (e.g. compel-style concatenation) so the full caption reaches SDXL. Tests whether a wider channel slows or changes convergence. A generator-side change, so it is a different arm, not a replication.

## E1 (SPEC2 §4): departures from A0, recorded 2026-10-18
- **D12 Hunyuan-DiT generator.** `Tencent-Hunyuan/HunyuanDiT-v1.2-Diffusers` (snapshot `5e96094e0ad19e7f475de8711f03634ca0ccc40c`, fp16) via diffusers `HunyuanDiTPipeline` at the pipeline's defaults: 1024×1024, 50 steps, guidance 5.0, DDPMScheduler, no negative prompt (the pipeline encodes an empty negative prompt itself), then LANCZOS to 512 and PNG as in A0. Each generator is run at its own defaults, which is what Hintze's 4×4 swap did; the SDXL cells keep A0's 25 steps. Seeds: same formula as A0 (D3). `src/generators/hunyuan.py`; records carry `prompt_tokens_mt5` as well as `prompt_tokens_clip`.
  - *Amendment 2026-10-19 (Brad, before any Hunyuan run beyond the 3-step smoke):* **25 steps, not 50, and `torch.compile` on the transformer.** The smoke measured 11.6 s per image at the 50-step default on the RTX Pro 6000 (batch 16), i.e. about 35 h and $90 per 100×100 cell; at 25 steps Hunyuan gets the same denoising budget as SDXL does in A0, and compile changes speed only. The 3-step smoke `e1_both_smoke` was run at 50 steps and is not used for analysis. Tencent's distilled 25-step checkpoint was rejected because step distillation can narrow sample diversity, the quantity under study. The Hunyuan cells skip the 20-trajectory pilot (the smoke is their only pre-check); the SDXL+Qwen cell keeps its pilot. Measured on the pod (`reports/e1_bench/hunyuan_throughput.md`): 11.3 s per image at 50 steps for any batch size 4–32, 5.4–6.3 s at 25 steps, 2.9 s at 25 steps with the transformer compiled (`mode="max-autotune-no-cudagraphs"`). The E1 runs use `compile_mode: default` (what the configs had when the queue launched E1-gen at 07:18): 3.5 s per image in the loop, about 13 min of compile at step 0 and again at the final partial batch; the extra 20% from max-autotune was not worth restarting a running cell for.
- **D13 Explicit CLIP-77 clip.** Every E1 cell clips the prompt to the longest word prefix with ≤ 77 tokens under SDXL's CLIP tokenizer before any generator sees it (`src/prompt_clip.py`; `prompt_clip.enabled` in the config). For SDXL this reproduces its own cut to within a partial word (SDXL cuts mid-token; we cut at the word boundary before it, so it reads at most one word less). For Hunyuan it imposes SDXL's channel width on a 256-token mT5 encoder. Records keep `prompt_raw` (the full caption), `prompt` (what the generator got) and the token counts before/after. A0 has `prompt_clip.enabled: false` and relies on SDXL's internal cut, as Hintze's code did.
- **D14 Qwen2.5-VL captioner.** `qwen2.5vl:7b` via the same Ollama path as LLaVA (same request: instruction, base64 PNG, `options={"temperature": 0.9}`), pinned to manifest digest `5ced39dfa4ba` (the digest shown by `ollama list`; the run refuses to start if the tag resolves elsewhere, `captioner.digest_prefix`). Ollama reports it as family qwen25vl, 8.3B parameters including the vision tower, Q4_K_M, 6.0 GB; LLaVA is Q4_0, so the quantisation differs with the model. Laptop test 2026-10-18 on four pilot images: 22 to 42 words per caption (it obeys the 50-word instruction), 2 to 3 s warm, no flags. Qwen2.5-VL 7B uses its own ViT, not CLIP, so the E1-both loop has no CLIP model on either side.
- **D15 E2-QZ: Chinese instruction, character budget and clip tokenizer.** The E2-QZ caption instruction is the Simplified Chinese translation of Hintze's instruction (SPEC2 §4 E2; DeepSeek translation, Opus 5.5 review, online native-reader check 2026-10-21 (strong affirmation; not a professional review, which is required before publication)), with "50 words or fewer" rendered as a 70-character budget (描述必须在70字以内). Why 70: a pod probe (2026-10-20, 30 captions) measured Hunyuan-DiT's bilingual CLIP at 1.03 tokens per Chinese character, so 70 characters plus punctuation sits under its 77-token limit as 50 English words do under SDXL's; at 80 about one caption in six would be clipped. The explicit clip (D13) uses the generator's own tokenizer in this cell (`prompt_clip.tokenizer: generator`, Hunyuan snapshot 5e96094e) instead of SDXL's, because the SDXL/OpenAI BPE tokenizer spends 2.6 tokens per Chinese character and would cut captions to about 30 characters, a third of the channel the English cells had. For CJK text the clipper cuts at character level and backs off to the last sentence or clause punctuation that keeps at least 60% of the fitting prefix (the word rule would have produced an empty prompt on text without spaces). New per-caption fields: `caption_chars`, `caption_cjk_share`, flags `over_limit_chars` and `not_cjk` (only when `captioner.limit_chars` is set). English cells are untouched: `tokenizer: sdxl` and the word rule remain the defaults. Seeds stay English, so step 0 is identical to E1-both.
- **D16 A0-S captioner has no temperature control.** The Messages API rejects `temperature`, `top_p` and `top_k` for `claude-sonnet-5-5` ("`temperature` is deprecated for this model", 400; tested 2026-10-20 with SDK 1.16.0, which also no longer exposes the argument). Hintze's loop and every other cell sample the captioner at T = 0.9; A0-S captions are sampled at the model's default, which cannot be set or read. The captioner records `temperature_applied: false` in every record and in the manifest's captioner info. Consequence for interpretation: the A0-S loop has whatever caption-side randomness the model provides by default; if A0-S shows deeper or fewer basins than A0 it may reflect this rather than the captioner's content prior, so the A0-S prediction below carries that caveat. The generator side (SDXL, its seeds, 25 steps) is unchanged. Everything else about the request matches Hintze's: the verbatim instruction, the PNG, no system prompt; the image is sent at 512 px (423 input tokens per call).

## E6 and Part 2 pilots: departures recorded 2026-10-20 (before any pilot run)
- **D17 Part 2 candidate mechanics (B-img pilot and arm A; SPEC2 §5).** `candidates.k` captions per step (K = 4, independent Ollama samples at T = 0.9, same instruction) and every candidate rendered; the chosen image is written as `step_NNN.png` with all candidates kept as `step_NNN.c<round>_<k>.png` and listed in the gen record (caption, clipped prompt, seed, file, sha256, SigLIP distance to the archive, rejected flag). Candidate seeds: `sdxl_base_seed + traj*10000 + step + (round*K + k)*10^8`, so round 0 candidate 0 is A0's seed for that (trajectory, step). Records of a K-candidate run carry `captions` (the K candidates) and `caption: null`; the caption that made the next image is step+1's `prompt_raw` (`analysis/common.caption_used`), and the last step uses its first candidate. Selection and the archive live in SigLIP space (`google/siglip-base-patch16-224`, revision 7fd15f06, pooled image embeds, cosine), steering only; DINOv2 and MiniLM remain the evaluation spaces (rule 4). Archive condition: at step t ≥ 5 (burn-in), the trajectory's images at t−4…t all within `radius_archive` of their normalised mean → image t enters the shared archive; entries act only on later steps (so the order of trajectories within a step does not matter). Reject rule: discard candidates within `radius_reject` of any entry; pick at random among the survivors (RNG seeded by `selection.seed`, trajectory, step and round); no survivor → recaption image t−1 K times and re-render, up to `resample` = 2 extra rounds; still none → advance the most distant candidate and mark the step `trapped`. Arm A: the same K candidates, one at random, no archive. The archive is rebuilt from the gen records on resume (each carries `siglip` and `archived`). The radii are the SigLIP values that reproduce the DINOv2 gravity radius 0.20 on A0-core (`analysis/siglip_calibrate.py` → `reports/siglip_calibration.md`); calibration on A0-core (100 trajectories, 9,500 five-step windows after burn-in): under DINOv2 0.20, 59.2% of windows satisfy the archive condition; the SigLIP radius with the same share is **0.078** (consecutive-pair matching gives 0.082; Spearman between the two distances 0.60 on windows, 0.54 on pairs; the two persistence decisions agree on 73.5% of windows). `radius_archive = radius_reject = 0.078`. Note for the readouts: at this radius the archive condition is met by most post-burn-in states in A0, so the archive grows quickly and the trapped rate is expected to rise early; that is the design in SPEC2 (R = the gravity radius), recorded here so a tighter radius in a follow-up is a deliberate change. In two_pass mode (laptop smoke only) every resample round releases the generator to caption; the pilot runs single_pass on the pod.
- **D18 E6 template seeds and one-shot sets.** E6 does not use Hintze's reservoir: `seeds.file` is a JSON table (`seeds/e6_loop.json`, `seeds/e6_oneshot.json`, written by `scripts/make_e6_seeds.py`) whose entries expand in file order to `reps` consecutive trajectories each; the trajectory → seed map (`seed_id`, `seed_rep`, `seed_set`, `seed_attrs`) is in the manifest and in every gen record. Seeds: "a photograph of {a young|an older} {light-skinned|medium-skinned|dark-skinned} {man|woman} working as {an airline pilot, in an airliner cockpit | a nurse, on a hospital ward | a social worker, in a community services office}, well lit, face visible" (36) and the portrait control "…, head-and-shoulders portrait, plain background, well lit, face visible" (12), 4 trajectories each, 20 steps. Tracking instruction = the Photo instruction with one sentence inserted after the first: "State the apparent age, gender and skin tone of any person." One-shot sets: 100 images each for "a photograph of {an airline pilot, in an airliner cockpit | a nurse, on a hospital ward | a social worker, in a community services office | a home health aide, in a client's home}, well lit, face visible" and 50 for Wilson, Ghosh & Caliskan's No-Stigma prompt verbatim ("a full color, front-facing photo of a person, neutral background, daylight"), run as a 1-step loop (`steps: 1`) so each image also gets a Photo caption. Generator seeds follow D3 with the trajectory index. Image coding: `analysis/skin_tone.py` (OpenCV YuNet 2023mar faces, score ≥ 0.6, largest face = primary; CelebAMask-HQ SegFormer `jonathandinu/face-parsing` on a 50 %-margin crop, skin = label 1; CIELAB via scikit-image, k-means k = 5 on ≤ 5,000 skin pixels, size-weighted mean of the three largest clusters → L*, h*, C*; C* < 5 flagged achromatic, h* unusable) differs from the paper's pipeline (whole-image CelebAMask GAN parser, 10 % skin cut) because loop images are whole scenes with small faces; the one-shot No-Stigma set validates it against the paper's SDXL figures. Gender presentation, age band and skin-tone band: `analysis/attribute_judge.py`, Claude Sonnet 5.5 (`claude-sonnet-5-5`, no temperature control, D16), image only, JSON answer; validated on a hand-labelled set before use. Smoke (`runs/e6_smoke`, 8 trajectories × 2 steps, laptop): the pipeline runs end to end; the step-0 images for "light-skinned" seeds came out medium-toned (olive) and LLaVA under the Tracking instruction described two of four as "of African descent" / "dark skin", after which step 1 rendered dark-skinned men (judge: medium → dark; L* 54 → 27). Skin tone is therefore always scored relative to the trajectory's own step 0 as well as on the absolute thresholds, and step-0 attribute presence is taken from the coders, not assumed from the seed.
- **D19 Text loops (E3) measurement notes.** E3 is a SPEC2 arm, not a Hintze replication; the records follow the same store rules. Three things to know when reading them: (1) `story_meta.flags.refusal` reuses the caption `REFUSAL_RE` and fires on dialogue ("I'm sorry", "I can't"); it is logged as-is and not used in the E3 report (every Sonnet call ended `end_turn`). (2) `story_words` and `summary_words` are whitespace counts; records where Qwen switched into Chinese (`cjk` flag, share of CJK characters > 5%) are undercounted and excluded from the length statistics. (3) MiniLM (`all-MiniLM-L6-v2`) embeds at most 256 word pieces, so a 500-word story is represented by its opening ~180 words; the E3-1 summaries (≤ 60 pieces) are embedded in full as `analysis/cache/<run>/minilm_summary.npz` and reported alongside. The atlas rules (k 40 joint, radius 0.15, hysteresis 1.25, dwell ≥ 5, present ≥ 3 visits) are the caption-space rules unchanged; `reports/e3.md` adds n-matched controls (image cells subsampled to 20 trajectories) because the text cells have 20 trajectories, not 100.
- **D20 Continuation runs (A0-1000, predictions.md 2026-11-10).** Hintze's loops are 100 steps; A0-1000 runs the A0-core loop on to step 999 to test whether the 100-step picture is stationary. The run directory `runs/a0_1000` is seeded with byte-identical copies of A0-core's steps 0–99 (records, gen records and images; `scripts/seed_continuation.py`, which verifies every image against its gen record's sha256, never overwrites, and appends provenance to `runs/a0_1000/continuation.jsonl`), so trajectory t of A0-1000 *is* trajectory t of A0-core continued: the runner resumes at step 100 with the caption of step 99 as the prompt and the same seed formula (D3; base + t·10000 + step, which is collision-free up to step 9999). A0-core itself is untouched. Parameters are A0-core's on the pod (single pass, SDXL batch 16, 8 LLaVA slots; `configs/a0_1000_runpod.yaml`, key `continue_from` is provenance only). Because a 1,000-step run writes about 40 GB and the pod volume is 100 GB, `scripts/runpod_offload.py` pulls the run to the laptop every 20 minutes and deletes from the pod only images already verified on the laptop (never records; the newest 3 images of each trajectory stay), so the laptop copy is the complete record and the pod copy is a working set. The pod copy is seeded with records for steps 0–99 and only the step-99 image (`runpod_sync.sh push-run a0_1000 99`). `analysis/gravity.py --window LO:HI` restricts the gravity statistics to a step window (endpoint = the window's last step); the hazard-by-step table uses 100-step bins when a run is longer than 100 steps.
  - *Amendment 2026-11-12 (pilot pod, recorded at the pilot gate):* the pilot pod ran Ollama server 0.40.16 (A0-core: 0.40.6; same llava digest 8dd30f6b0cb1) with `OLLAMA_CONTEXT_LENGTH=8192` per slot (A0-core: the 32,768 default). At 32k × 8 slots the KV cache pushed 8 of llava's 33 layers onto the CPU beside SDXL on the 48 GB A6000 (commit 9ccadf2). The only effect on the data is where a runaway caption is cut (8k instead of 32k tokens); CLIP reads the first 77 tokens either way. The pilot had 4 such cutoffs in 18,000 captions. The pod's volume disk was 50 GB (no network volume), so the offload loop ran as described above.
